# resume.md — сравнительный анализ: ai-challenge-09 vs llm-agent-app

Сравнение двух реализаций агента с памятью, контекстными стратегиями и конечным автоматом задачи:

| | **ai-challenge-09** (этот репозиторий) | **llm-agent-app** |
|---|---|---|
| Backend | Python 3.12, FastAPI + uvicorn + sse-starlette, asyncio, SQLite (sqlite3) | Kotlin, Spring WebFlux (реактивный), SQLite (JdbcTemplate) |
| Frontend | Vue 3 + pinia + vite | React + TS |
| Транспорт | SSE (поллинг состояния агента из насоса) | SSE (прямая трансляция событий от ядра) |
| Тесты | 228 pytest + vitest (фронт) — **проверено: зелёные** (pytest 6.3s, ruff, mypy strict — чисто) | есть, объём меньше |
| Документация | my_agent.MD (384), BACKEND.md (169), WEB_UI.MD — спека с обоснованием решений | docs нет (только код) |

Метод: полный код-ревью обоих backend'ов (ядро агента, память, FSM, транспорт, сторы), фокус на архитектуру, память и автомат задачи. По llm-agent-app ранее составлен стек-независимый план `be-agent.md` — здесь сравниваются фактические реализации.

## 1. Вердикт кратко

**ai-challenge-09 сильнее** по архитектуре слоёв, памяти (проектная LTM, инварианты, подтверждение подсказок памяти), FSM (подтверждение плана пользователем, валидационные шаги, история переходов), конкурентности (busy-lock на агента), персистентности (FK, атомарные снапшоты, миграции), LLM-клиенту (ретраи, совместимость провайдеров, учёт токенов) и субагентам (делегирование есть — у конкурента нет вовсе).

**llm-agent-app сильнее** в нескольких точечных решениях: событийный контракт SSE (типизированные события, sequence, runId/stepId), кооперативная пауза выполнения в контрольных точках, стратегия веток в контексте, история саммари (несколько поколений), политика fail-open/fail-fast как осознанный документ.

Итог: **~70/30 в пользу ai-challenge-09**. Ниже — детали и что перенять.

## 2. Архитектура: слои и связность

### ai-challenge-09 — чисто, образцово

Разделение честное, зависимость направлена внутрь:

```
core/ (Agent, ContextBuilder, Compactor, TaskState) — plain Python + asyncio, БЕЗ web-зависимостей
memory/ (session, persistence, facts, longterm, branching)
tools/ (registry + инструменты, привязка через конструктор)
web_server/ (app, state, stream, dto) — только транспорт
```

- `Agent` (838 строк) — единый связный класс, а не god-class. Петля, компакция, факты, usage — в одном месте, но с ясной внутренней структурой и WHY-докстрингами.
- `WebState` — реестр агентов по вкладкам; `agent_id` (uuid, стабилен) ≠ `session_id` (автосохранение). Восстановление после рестарта сервера.
- Общие ресурсы (LLMClient, ToolRegistry, Config, SessionStore) — шаред-синглтоны на процесс.
- **llm-agent-app — противоположность:** `AgentImpl.kt` ~1240 строк — god-class: петля + сборка контекста + суммаризация + факты + FSM + workflow-директивы + промпты в одном классе. Именно этот опыт зафиксирован в `be-agent.md` §2 как анти-пример.

**Вывод:** слоёв у ai-challenge-09 — «как в учебнике». Что улучшить: web_server всё же знает внутренности агента глубже, чем нужно (насос поллит `streaming_text`, `compaction_note` — см. §8).

## 3. Конечный автомат задачи

### Сравнение машин

| Аспект | ai-challenge-09 | llm-agent-app |
|---|---|---|
| Фазы | IDLE→PLANNING→EXECUTION→VALIDATION→DONE | planning→execution→validation→done |
| Граф | с возвратами: execution→planning, validation→{execution,planning,done} | строго линейный, только вперёд |
| Подтверждение плана | **есть**: `PLANNING→EXECUTION` только при `plan_confirmed=True`; подтверждает **пользователь** кнопкой UI (`confirm_plan`), не модель | нет |
| План | `steps` + отдельный `validation_steps`; смена группы списков сбрасывает `step` | единый план с типами шагов, обрезка 2000 символов молча |
| История переходов | `list[TaskTransition(from, to, note)]` | нет |
| Пауза | флаг `paused` ортогонален фазе + `expected_action` + PHASE_PROTOCOL («продолжить без повторных объяснений») | `workflow_paused` — кооперативная пауза в контрольных точках петли |
| Состояние vs машина | `TaskState` (dataclass) и `TaskStateMachine` (валидатор) — **раздельные** классы | один стор-компаньон с валидацией |
| Пути записи | 9 LLM-инструментов + REST `POST /task` → **одна машина, один валидатор** | tool + REST → один валидатор (общее решение) |
| Директивы модели | PHASE_PROTOCOL инжектится SYSTEM-блоком каждый ход: что можно/нельзя в каждой фазе | аналогичные workflow-директивы |

### Оценка

**ai-challenge-09 сильнее по существу:**
1. **Подтверждение плана пользователем** (`plan_confirmed`, `agent/core/task.py`) — переход в исполнение невозможен без действия человека через UI. У llm-agent-app модель сама переходит planning→execution. Это принципиальный контроль «человек в контуре».
2. **Отдельный план валидации** (`validation_steps`) — фаза проверки получает собственный чек-лист, а не переиспользует план выполнения.
3. **Обратимые переходы** (validation→execution для правок, validation→planning для корректировки плана) — реалистичный workflow; у llm-agent-app строго линейный граф, что вынуждает сброс задачи.
4. **История переходов с заметками** — аудируемость.
5. Митигирован общий недостаток обоих проектов: у обоих `Tool.execute(arguments)` не получает контекст запуска (session/run). llm-agent-app решает перехватом инструмента по имени строки (хрупко); ai-challenge-09 — замыканием инструментов на сессию в конструкторе (`task_tools(memory)`) — чище и без хака.

**Что у llm-agent-app лучше:** кооперативная пауза — `workflow_paused` реально останавливает петлю в контрольных точках (между шагами, перед сменой tool→LLM). В ai-challenge-09 пауза — только протокольная конвенция (флаг + ожидаемое действие + текст в промпте): запущенный стрим остановить нельзя, модель сама «должна» уважать флаг. Это разные философии; конвенция проще, но не даёт гарантий.

## 4. Контекст: сборка и стратегии

### Общее (оба сделали правильно)
- Единая точка сборки контекста: `ContextBuilder.build_messages` / контекст-ассемблер AgentImpl. Фиксированный порядок блоков: system → память → ограничения → задача → саммари → история.
- Проекция ≠ чат: сжатие не трогает историю (llm-agent-app — upto_id граница; ai-challenge-09 — `compacted_upto` указатель). Полная история сохраняется всегда.
- Саммари — отдельный блок перед хвостом истории.

### ai-challenge-09 — точнее в измерении

- **Калибровка токенизатора** (`_token_ratio` = фактические prompt_tokens API / локальная оценка chars/4, clamp 1..4): локальная оценка для русского занижена в 1.5–2 раза — агент это *измеряет* и масштабирует бюджет компактора. Дополнительно: детекция серверной обрезки (`prompt_tokens < 0.7×отправленного` → триггер компакции). llm-agent-app: только chars/4, калибровки нет, оценка переполнения не делается вовсе (осознанно).
- Бюджет компакции считается явно: `окно×0.4 − system×ratio − прежнее_саммари×ratio − slack`, tail ≥ MIN_KEEP=2, отдельный max_tokens с запасом под thinking-модели, различение пустого саммари и `finish_reason=length`.
- **Учёт токенов** — лучший из виденного: точный usage + reasoning_tokens из `completion_tokens_details`, фолбэк с пометкой `~`, суммарные in/out/Σ включают вызовы компакции и фактов, обрезка ответа детектируется.
- Триггер компакции двухканальный: проекция превысила порог ИЛИ сервер начал выбрасывать историю.

### llm-agent-app сильнее в одном: стратегии как конфигурация

- 5 стратегий на сессию (none/sliding_window/sticky_facts/summary/branching) с резолвом эффективной (legacy-фоллбэк: none+компакция→summary).
- **Стратегия branching**: в контекст injected'ятся резюме неактивных веток — агент «помнит» альтернативные линии диалога. В ai-challenge-09 ветки есть только как модель данных (fork/switch), неактивная ветка никак не представлена в контексте.
- История саммари: `session_summaries` хранит несколько поколений (upto_order), саммари можно откатить. В ai-challenge-09 саммари одно, перезаписывается.

**Вывод:** точность контекст-менеджмента — у ai-challenge-09; вариативность стратегий — у llm-agent-app. Для ai-challenge-09 разумно взять: (а) branching-стратегию поверх существующих веток, (б) опциональный sliding_window как выбор пользователя.

## 5. Память: слои и записи

### Таблица слоёв

| Слой | ai-challenge-09 | llm-agent-app | Кто лучше |
|---|---|---|---|
| Долгосрочная | **project-level** SQL, инжект SYSTEM-блоком | global (на всех проектов) | ai-challenge-09: изоляция между проектами правильна |
| Запись в долгосрочную | только явное действие UI **или принятая пользователем** подсказка модели (MEMORY_SUGGESTION → плашка подтверждения) | только пользователь | ai-challenge-09: у модели есть голос, у человека — вето. Лучший UX из двух |
| Рабочая | scratchpad (инструменты write/append/read, лимит 8000) | working memory (проектная, только пользователь) | ниша та же; у llm-agent-app жёстче право записи |
| Факты | 1 LLM-вызов на сообщение юзера, replace-all, при ошибке старые факты сохраняются | sticky_facts: то же + слепой один ретрай | паритет (и та же слабость — см. §11) |
| Инварианты | **первоклассный слой**: список ≤50, блок-констрейнты, питают фазу валидации | часть профиля/инвариантов в контексте | ai-challenge-09: инварианты прямо связаны с FSM-валидацией |
| Саммари | одно, перезапись с merge прежнего | поколения summaries (upto_order), не выдаются через API | llm-agent-app |
| Ветки в контексте | нет (ветки — только данные) | branching-стратегия | llm-agent-app |

### Ключевые различия

1. **Подтверждение подсказок памяти** — механизм ai-challenge-09, которого нет у конкурента: модель в конце ответа может предложить факт, фронтенд показывает плашку «принять/отклонить», принятое падает в проектную LTM. Закрывает главную дыру «автоматической памяти» — мусор от модели. Стрим при этом чистится от маркера (holdback частичного маркера в стриме).
2. **Проектная изоляция LTM** правильнее глобальной: у llm-agent-app `LongTermMemoryStore` — один на всё.
3. Оба проекта согласованно решают: память пишут инструменты/пользователь, модель не пишет напрямую (кроме подтверждаемой подсказки). Оба: replace-all для фактов (осознанный компромисс).

## 7. Конкурентный доступ и жизненный цикл запуска

- **ai-challenge-09:** один активный запрос на агента — `AgentBusyError` → 409; `cancel_ask()` через `task.cancel()`; отключение SSE-клиента **не** убивает ход (докрутится, автосохранение зафиксирует); ошибка → rollback счётчиков usage; отмена сохраняет частичный ответ с маркером.
- **llm-agent-app:** блокировки на сессию нет вообще — два параллельных запуска перемешают историю и голову ветки (критичный баг, зафиксирован в be-agent.md §14).

**ai-challenge-09 выигрывает**, но есть микродыра: в `send_message` проверка `is_streaming` и старт — не атомарны (двойной клик может проскочить между ними). Мелочь, но дешевле закрыть атомарным start-ом.

## 8. Транспорт (SSE)

| Аспект | ai-challenge-09 | llm-agent-app |
|---|---|---|
| Механика | **насос-поллинг**: каждые 100мс опрос публичного состояния агента (стрим-текст, очереди событий) → дельты | прямая трансляция: события ядра → SSE |
| Контракт | события внутри data-JSON (поле `event`), 17 типов | типизированные события с `sequence`, `runId`, `stepId` |
| Структурность | `compaction_done` парсится **regex из текстовой заметки** — строковый контракт ядро↔транспорт, хрупко | payload структурен от рождения |
| Задержка | до 100мс + busy-wait на открытый стрим | мгновенно |
| Разрыв соединения | ход продолжает жить (осознанно, задокументировано) | похоже |

- **Модель событий llm-agent-app лучше как контракт** (typed payload, sequence для порядка, runId/stepId для сопоставления) — но её реализация тонет в god-class'е.
- **Фронтенд ai-challenge-09 лучше:** надёжный SSE-парсер (CRLF, комментарии, мультистрочный data, частичные буферы), батчинг дельт 100мс, **общий редьюсер `applyStreamEvent`** для стора и компоузабла (один источник истины трансформации событий — тестовый двойной контур), AbortController + серверная отмена.

## 9. Инструменты и LLM-клиент

**Инструменты.** У обоих `execute(args)` без контекста запуска — общий дизайнерский долг (лечится `execute(args, ctx)` в обоих). Реестры: у llm-agent-app найден реальный баг — KDoc обещает приоритет встроенных инструментов, код отдаёт приоритет динамическим (MCP мог бы затенить встроенный task_state). У ai-challenge-09 реестр — простой словарь overwrite-last-wins; риска нет только потому, что MCP — заглушка. **При реализации MCP правило «статические всегда сильнее динамических» обязательно перенести.**

**LLM-клиент ai-challenge-09 заметно взрослее:**
- ретраи 3× (1/2/4с) только на {408,425,429,5xx, transport, SSE} и только до первого чанка; 400/401 — сразу наверх;
- совместимость провайдеров: нормализация reasoning-полей GLM (`reasoning`) и DeepSeek (`reasoning_content`), fallback-ретрай без `stream_options` при 400;
- ошибка провайдера внутри HTTP 200 SSE распознаётся как LLMError;
- детекция обрезки контекста сервером → триггер компакции;
- учёт reasoning_tokens thinking-моделей.

llm-agent-app: интерфейс стрима есть, устойчивость к провайдерам на этом уровне не развита.

**Ключевая находка петли ai-challenge-09:** последний из MAX_TOOL_ROUNDS=5 раундов выполняется **без инструментов** — модель обязана завершиться текстом, висячий `tool_call` невозможен структурно. Элегантное решение, которого нет у llm-agent-app (там лимит итераций просто рвёт петлю). Плюс guard на пустой ответ thinking-моделей (max_tokens съеден рассуждениями, `finish_reason=length`) — отдельная диагностика с подсказкой.

## 10. Субагенты / мультиагентность

- **ai-challenge-09:** делегирование есть и сделано безопасно: `delegate` создаёт эфемерного субагента (профиль = системный промпт, свежая сессия, **без инструментов** → рекурсия невозможна по построению), активность течёт в SSE (`subagent_started/delta/done`), `list_subagents`, профили как пул ролей с привязкой к проекту. Делегирование разрешено только в EXECUTION/VALIDATION — связано с FSM.
- **llm-agent-app:** мультиагентности нет.

Полное преимущество ai-challenge-09. Единственное: состояние проекта (задача, scratchpad) остаётся у оркестратора — субагент не видит его (контекст передаётся явно полем) — это правильный выбор, но стоит задокументировать лимит: субагент не помнит прошлые вызовы.

## 11. Что улучшить в ai-challenge-09 (приоритизировано)

### P1 — транспорт и хранилище (заметная цена сегодня)

1. **Убрать поллинг из SSE-насоса** (`agent/web_server/stream.py`, 100мс). Агент уже однопоточный по активностям — заменить опрос очередей на `asyncio.Event`/`asyncio.Queue`: ядро сигнализирует, насос спит до события. Уйдут и задержка, и busy-wait на каждый открытый стрим.
2. **Убить строковый контракт заметки компакции.** `compaction_done` собирается regex-парсингом человекочитаемой строки. Пусть ядро кладёт в очередь структурный payload `{removed, summary_tokens, pct_before, pct_after}`, а текст заметки формируется на границе транспорта (как в llm-agent-app: структурный event + текст отдельно).
3. **Инкрементальная персистентция вместо полного снапшота.** Снапшот — DELETE+INSERT всех сообщений: O(n) на каждый dirty-тик, растёт с историей. Достаточно: upsert строки сессии + INSERT новых `seq` + DELETE хвоста при ветвлении. Атомарность сохранить транзакцией.
4. **Не блокировать event loop SQLite.** `sqlite3` + `threading.Lock` вызываются прямо в асинхронном контексте (finally стрима, цикл автосохранения). Минимум: `PRAGMA journal_mode=WAL` + перенос операций стора в `asyncio.to_thread`. Сейчас локально незаметно, при двух параллельных стримах — уже джиттер.
5. **Атомарный старт запроса.** В обработчике `messages` проверка `is_streaming` и старт разделены — гонка двойного клика. `start_ask` должен сам атомарно проверять-и-занимать (или `asyncio.Lock` per-agent) — тогда 409 гарантирован, а не ошибка внутри SSE.
6. **Один persist на ход.** Сейчас снапшот пишется и в finally стрима, и автосейвом. Fingerprint смягчает, но двойная точка записи — лишняя.
7. **Персистентные счётчики токенов.** `in/out/Σ` живут только в рантайме — перезагрузка страницы обнуляет. Колонки в `sessions` — тривиально.

### P2 — память и контекст (перенять у llm-agent-app)

8. **Branching-стратегия контекста:** при активной ветке инжектить краткое резюме неактивных (у llm-agent-app — резюме веток в блоке контекста). Данные веток уже есть (BranchState с summary) — не хватает только инжекции.
9. **Политика слияния фактов:** сейчас replace-all (факты на сообщение затирают предыдущие). Минимум — merge по ключу как у sticky_facts llm-agent-app (своё решение тоже replace-all, но там это зафиксировано как осознанный компромисс — задокументировать и здесь).
10. **Миграции как версионированный список.** Сейчас `_MIGRATIONS` — список ALTER внутри стора. Работает, но при росте схемы нужен порядок версий + тест «с нуля» и «с промежуточной версии» (llm-agent-app показал, к чему приводит размазанность — дубли создания таблиц).
11. **Ранжирование LTM при инжекте:** сейчас весь блок целиком (задокументировано, объём мал). Точка расширения — перехватывается легко: в `ContextBuilder` уже есть слоты под rag/memories-стабы.

### P3 — на вырост

12. **`Tool.execute(args, ctx)` до реализации MCP.** Сейчас инструменты привязаны к сессии в конструкторе — хватает. Но MCP-инструменты придут динамически, и без контекста запуска повторится история llm-agent-app (перехват по имени). Дешевле поменять интерфейс заранее + сразу правило «статические затеняют динамические» в реестре.
13. **История саммари** (поколения с границей upto) — даёт откаты компакции и диагностику деградации. Опционально.
14. **Кооперативная пауза стрима** — флаг `paused` сейчас уважается моделью по протоколу, но не останавливает запущенный стрим. Если пауза «на ходу» нужна — контрольные точки между раундами петли (как workflow_pause у llm-agent-app). Текущая конвенция честно проще; менять стоит только при реальной потребности.
15. Мелочи: auth отсутствует (для localhost допустимо), id сообщений `m{idx}` сдвигаются при fork (клиент ресинхронизируется полным списком — работает, но sequence-номера как в llm-agent-app сделали бы диффы надёжнее).
