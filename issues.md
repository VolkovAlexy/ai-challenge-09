# issues.md — доработки ai-challenge-09 (по анализу resume.md)

Проведён разбор фактической реализации: каждый пункт из `resume.md §11` сверен с
кодом, оценены **целесообразность** (ценность изменения) и **сложность**, приоритеты
пересмотрены относительно исходного P1/P2/P3. Источник — только текущий код.

Приоритеты:
- **P1** — высокий ROI: низкая сложность и/или реальный дефект. Делать первыми.
- **P2** — ценно, заметный объём работ.
- **P3** — на вырост / опционально.

## ISSUE-1: Атомарный старт запроса (гоночный busy-check) — **P1**

`agent/web_server/app.py:255` → проверка `is_streaming`, затем в `stream.py:116`
`start_ask`. Между ними — асинхронный зазор.

- **Целесообразность:** высокая. Это реальная гонка: два параллельных
  `POST /messages` для одного агента могут оба пройти проверку до того, как
  любой из генераторов вызовет `start_ask` (sync-хендлер `send_message` в
  threadpool, `start_ask` — на event loop). Тогда второй ход не получит HTTP 409,
  а деградирует до SSE-события `error` (stream.py:117–119) или стартует второй
  вывод. У `delete_agent` (app.py:134) та же неатомарная проверка.
- **Сложность:** низкая.
- **Где:** `agent/core/agent.py:363-368` (`start_ask`), `agent/web_server/app.py:255-258,134`,
  `agent/web_server/stream.py:116-119`.
- **Что менять:** сделать «проверить-и-занять» атомарным. Проще всего — ввести
  явный флаг `self._busy: bool`, который `start_ask` синхронно выставляет и
  снимает в `finally`; `is_streaming` оставить как производное. `start_ask`
  должен сам возбуждать `AgentBusyError` без повторной проверки снаружи.
  `send_message` — убрать/ослабить проверку, положившись на `AgentBusyError`
  (мапить в HTTP 409).
- **Риски/замечания:** менять только точку владения флагом; не сломать
  `cancel_ask`/отмену. Test-ов на гонку нет — добавить тест с двумя
  конкурирующими стартами.
- **Тесты:** `tests/test_web_server.py` (send_message), `tests/test_agent.py`.

## ISSUE-2: Не блокировать event loop SQLite (WAL + to_thread) — **P1**

`agent/memory/persistence.py:145` — синхронный `sqlite3.connect`, все вызовы
`self._conn.execute(...)` блокирующие, под `threading.Lock`. Вызываются прямо в
асинхронном контексте.

- **Целесообразность:** высокая. Прямые блокирующие вызовы БД в `finally`
  стрима (`stream.py:237 state.persist`) и в цикле автосейва (`app.py:49`
  `persist_if_dirty`). При одном агенте незаметно; при двух параллельных
  стримах — видимый джиттер. Включение WAL практически бесплатно и убирает
  конфликты читатель/писатель.
- **Сложность:** низкая–средняя.
- **Где:** `agent/memory/persistence.py:147-151` (PRAGMA), все методы стора;
  вызовы из `agent/web_server/stream.py`, `agent/web_server/app.py`,
  `agent/web_server/state.py`.
- **Что менять:** минимум — `PRAGMA journal_mode=WAL` (одна строка). Желательно —
  обернуть тяжёлые операции (`snapshot`, `list`, `delete`, миграции) в
  `asyncio.to_thread`, либо вынести весь доступ к `SessionStore` в отдельный
  поток/очередь. `WebState.persist` при этом становится `async` — это
  затрагивает все вызовы (`create_agent`, `persist_if_dirty`, endpoints).
- **Риски/замечания:** не смешивать два коннекта; WAL требует, чтобы все
  обращения шли через один `sqlite3.Connection` (уже так). Переход `persist` в
  async — самая расползающаяся часть.
- **Тесты:** `tests/test_session_store.py`, `tests/test_web_server.py`.

## ISSUE-4: Политика слияния facts вместо replace-all — **P1**

`agent/core/agent.py:774` → `self.memory.facts = result.facts` — полная замена
набора фактов на каждое сообщение пользователя.

- **Целесообразность:** средняя–высокая. Replace-all теряет факты, которые модель
  при обновлении не решила повторить. Merge по ключу (обновить существующие,
  добавить новые, удалить только явно помеченные) надёжнее и дешевле.
- **Сложность:** низкая.
- **Где:** `agent/core/agent.py:749-786` (`_update_facts`),
  `agent/memory/facts.py:49-79` (`parse_facts`), `agent/memory/session.py:69`.
- **Что менять:** в `_update_facts` слить: `merged = {**old, **new}`; удаление
  ключа — отдельным маркером (например, значение `""`/`__delete__` в ответе
  модели и инструкция в `FACTS_EXTRACTOR_PROMPT` `facts.py:21-30`). Как минимум —
  merge и задокументировать компромисс (как сделано у llm-agent-app).
- **Риски/замечания:** меняется контракт с моделью — обновить промпт, чтобы
  «не упомянул в ответе» не означало «удали». Иначе накопительный рост.
- **Тесты:** `tests/test_facts.py`.

## ISSUE-9: Убрать поллинг из SSE-насоса — **P2** (переоценка вниз)

`agent/web_server/stream.py:22,168-195` — `POLL_INTERVAL=0.1`, busy-wait на
каждом открытом стриме; агент поллится по публичному состоянию.

- **Целесообразность:** средняя, а не высокая. Выигрыш — задержка ≤100 мс и
  отказ от постоянного опроса. Для чата 100 мс некритично, а это самый большой
  по охвату рефакторинг, трогающий «ядро не знает про web» (AGENTS.md). Сейчас
  «новый раунд» детектится обнулением длины `streaming_text` (stream.py:181-184),
  компакция/субагенты/память — диффом состояния. При переводе на событийную
  модель всё это надо воспроизвести как события.
- **Сложность:** высокая. `Agent` должен пушить дельты в очередь (`asyncio.Queue`),
  нужны события начала/сброса раунда, компакции, субагентов, memory_suggestion.
- **Где:** `agent/web_server/stream.py` (весь), `agent/core/agent.py` (lifecycle).
- **Рекомендация:** отложить до стабилизации ISSUE-2/3. Делать только под тесты
  (`tests/test_web_server.py:214` гоняет `agent_stream`). Прежде чем браться —
  оформить отдельным планом, т.к. меняет документированную архитектуру.
- **Тесты:** `tests/test_web_server.py`.

## ISSUE-10: Инкрементальная персистентность вместо полного снапшота — **P2**

`agent/memory/persistence.py:241-245` — `DELETE FROM messages` + полный
`INSERT` всех сообщений на каждый dirty-тик: O(n) и растёт с историей.

- **Целесообразность:** средняя. Write amplification реальна, но при типовых
  размерах чата (десятки сообщений) не критична. Главное — атомарность уже
  обеспечена транзакцией.
- **Сложность:** высокая. Нужно инкрементально: upsert строки `sessions` +
  `INSERT` новых `seq` + `DELETE` хвоста при ветвлении/обрезке. Но `branches`
  сериализуются в `branches_json` целиком (persistence.py:184-194,232) — при
  инкрементальном подходе это осложняется; семантика «полная замена» проста и
  надёжна, ошибки в инкременте дороже.
- **Где:** `agent/memory/persistence.py:158-245` (`snapshot`),
  `agent/memory/session.py` (обрезание веток).
- **Рекомендация:** ценность невелика при росте истории; браться только при
  реальном объёме сообщений. Если делать — вместе с ISSUE-2/8 и покрыть тестами
  все сценарии добавления/обрезки/ветвления.
- **Тесты:** `tests/test_session_store.py`, `tests/test_branching.py`.
